Making a Coding Agent Predict the Outcome of Its Environment and Update Its World Model

X · jayzenith.me · GitHub repo

The setup: a predict-and-decide agent (Arm B) makes a PREDICTION on what its own patch will do, then chooses to either KEEP or REVISE the patch. The patch is executed either way, and a cross-entropy loss on the verified outcome trains the prediction directly while GRPO handles the rest. The matched comparator is test-and-recover (Arm A): patch, test, react.

Work in progress: RLVR beat SFT for both agents, and the prediction mechanism shows some learning. The SFT checkpoint called PASS on 100% of candidates, which needs to be corrected in the SFT process: 257 of its 302 prediction labels are PASS. But cross-entropy on verified execution outcomes did create a RUNTIME_ERROR detector: 62.5% and 64.1% precision across the two seeds, against a 16% base rate, off 8 demonstrations. ASSERTION_FAILURE, 57% of all outcomes, stayed at zero, never predicted once at any checkpoint.

Architecture

One harness, two agents

Both arms share one harness. Arm A reacts to python_test output. Arm B predicts the outcome and commits to KEEP or REVISE. The verified-label auxiliary CE follows ECHO (Shrivastava et al., 2026). Built on PRIME-RL and Verifiers, V1 environments.

Dataset design

What the agent was built and trained on

The pipeline was built from scratch

MBPP is ~1,000 short Python problems with gold test assertions (Austin et al., 2021). PREDICT is a multi-turn tool-using agent on Qwen3-4B-Base: hand-designed SFT traces (direct-solution, two-step recovery, prediction labels, KEEP/REVISE paths), the environment, the auxiliary-loss wiring, and the full SFT→RL pipeline.

Training set, validation set, eval set

Split 212 SFT / 212 RL, plus 40 validation and a 500-problem test set, scored once after every design decision was frozen. The RL stage never trains on a problem SFT already saw. 212 traces per arm is enough to install an agent protocol. Teaching the outcome classes is a separate job the SFT process only half did: the agent may predict 6 classes, but the SFT traces demonstrate 3, and SYNTAX_ERROR and TIMEOUT appear zero times.

Diagnosis

What RLVR actually changed

Where the gain landedThe measured gain sits entirely on the first patch. Recovery I can't call either way. The first patch fails on about 270 of the 500 tasks, and the agent then goes on to fix about 40 of them. Forty events is too few to detect a change of a few points, so recovery could have improved and I would not see it.

The prediction itselfThe gate works: REVISE follows a non-PASS prediction 100% of the time, KEEP follows a PASS prediction 96–99%. The open question is whether the prediction is any good. At RL step 100, seed 42:

Recall = how often the model's own prediction matched what actually happened. RUNTIME_ERROR went from never predicted at SFT to 63% recall, and it isn't recall bought by over-predicting: 62.5% precision (64.1% on seed 43) on a class that occurs 16% of the time, calling it 208 times against 207 real. ASSERTION_FAILURE, the most common outcome, was never predicted correctly once, not at SFT and not at any RL checkpoint. Both movements replicate across seeds.

It saw plenty of failuresAcross Arm B's RL training rollouts (15,122 verified labels), its own patches failed about 70% of the time. It still predicted the failure classes at nowhere near their real rate:

ASSERTION_FAILURE is the single most common thing that happens and the model calls it 3% of the time. RUNTIME_ERROR it calls at almost exactly the right rate. The SFT process says the same thing backwards: ASSERTION_FAILURE was demonstrated 4.6× more often than RUNTIME_ERROR (37 labels to 8), and RUNTIME_ERROR is the one that came back. So it isn't scarcity. The bottom two rows aren't results at all, since SYNTAX_ERROR and TIMEOUT were never trained on.

What this shows
The prediction adds nothing here. Arm B predicts PASS on all three candidates and is wrong on the first two, so it reacts to each failure exactly as a test-and-recover agent would. This is the 0% ASSERTION_FAILURE recall above, in a single trace.
Verifier gap
The third candidate, z = x * y, uses the exact operator the task banned. The test checks numeric output only, so it scores reward 1.0 anyway. Arm A's solution for the same task (repeated addition with sign correction) actually obeys the instruction. One isolated case, not a systemic pattern, but a reminder that the reward grades less than the task asks for.

What this taught

Three things

  1. The eval has to make the rare thing happenMBPP is too easy to measure recovery. Every rollout writes a first patch, so 500 tasks measure that fine. Recovery only fires when the patch fails, which happens on ~270 of the 500, and it succeeds ~40 times. The fix isn't only more tasks, it's harder ones: on problems the agent can't one-shot, every task exercises recovery.
  2. Post-training can only reinforce what SFT made emittable CE had ideal conditions and still only landed one class. The loss was on the verified outcome with RLVR masked off those tokens, nothing competing with it, and RUNTIME_ERROR came back off 8 demonstrations. ASSERTION_FAILURE never did off 37. So it isn't the loss and it isn't the count: SFT never made the model able to tell "this code runs but the answer is wrong" apart from PASS, and no downstream loss can reinforce a distinction the model can't make.
  3. One seed is not a resultThe second seed is what separates the real effects here from the noise. On seed 42 Arm A beat Arm B at step 100, 56.4% vs 52.0%. On seed 43 the two arms land at 54.2% and 53.6%, p=0.86, so that gap was noise. The within-arm SFT-to-RLVR gains replicated across both seeds in both arms, so those are real.

Follow-up experiments

Where this goes next

Straight from the diagnosis: the SFT process never demonstrated half the outcome classes, and barely demonstrated the one that dominates.

Teach all six classes

The SFT traces demonstrate PASS, ASSERTION_FAILURE and RUNTIME_ERROR, and never show SYNTAX_ERROR or TIMEOUT once. Before any conclusion about what the predictor can't learn, it should be shown every class it is asked to emit. ASSERTION_FAILURE is 37 of the 302 prediction labels in the SFT set (12%) against 57% of real outcomes, so it needs far more. This is a data-generation change, not a training change, so it is the cheapest fix here.
