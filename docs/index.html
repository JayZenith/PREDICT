PREDICT

Reactive vs. Predictive Post-Training for Coding Agents

X · jayzenith.me · GitHub

When does teaching an agent to predict the consequence of an action actually improve its behavior?

PREDICT compares two Qwen3-4B coding agents trained on the same environment, tasks, reward, and SFT → RL pipeline.

Arm A is reactive: patch, test, recover.

Arm B is predictive: patch, predict the verified outcome, choose KEEP or REVISE, then execute. It is trained with GRPO plus an auxiliary cross-entropy target from the outcome the verifier confirms afterward.

Arm B did not outperform the reactive baseline. The interesting part was how it failed. The predictive agent learned a real outcome distinction, but trajectories that acted on that prediction through REVISE almost never recovered.

On MBPP, predicting the outcome offered little advantage over simply running the test. Testing cost one tool call and returned the same information the model was trying to predict. REVISE also consumed a call without returning that feedback.

Agent design

Two agents, one environment

The tasks, tools, reward, and evaluation are shared between both arms.

Arm A follows the standard loop:

patch → test → observe → recover

Arm B inserts prediction before execution:

patch → predict outcome → KEEP or REVISE → execute

Arm B predicts one of six outcome classes:

PASS
ASSERTION_FAILURE
RUNTIME_ERROR
SYNTAX_ERROR
TIMEOUT
OTHER

If the agent chooses REVISE, the rejected patch is still executed in the background so the training system can recover a verified outcome label. That result is not shown to the agent during the rollout.

Experiment

Qwen3-4B-Base on MBPP, SFT then RLVR

Both arms were trained with two RL seeds. The final test set was evaluated after the experimental design was frozen.

The experiment was intentionally narrow: one model family, one coding environment, two RL seeds, and a limited post-training budget.

MBPP is about 1,000 short Python problems with gold test assertions (Austin et al., 2021), split by seed 42.

Result

Neither arm established an overall advantage

Both agents improved over their own SFT checkpoints. The apparent Arm A advantage in seed 42 did not replicate in seed 43, so this experiment does not establish an overall pass@1 advantage for either protocol.

Arm A: seed 42, 56.4%; seed 43, 54.2% Arm B: seed 42, 52.0%; seed 43, 53.6%

The main finding

The deficit concentrates in the REVISE path

For Arm B, trajectories that never used REVISE passed:

63.3% in seed 42
60.4% in seed 43

Trajectories that used REVISE at least once passed:

1.1% in seed 42
4.9% in seed 43
seed 42 seed 43

Greedy pass@1, step 100. Arm B's headline 52.0% is almost exactly 409 × 63.3% out of 500: the never-revised trajectories carry nearly the entire score.

The gate was not random. It chose REVISE more often when the patch would actually fail:

seed 42: 22.2% on failing patches vs. 8.5% on passing patches
seed 43: 14.3% on failing patches vs. 4.2% on passing patches

But acting on that signal was expensive.

⚠ REVISE spends a call and returns nothing
REVISE also consumed a call without returning that feedback. 99% of REVISE trajectories exhausted the 8-call budget in seed 42 and 95% did so in seed 43. For trajectories that never revised, those numbers were 35% and 37%.
The protocol created a bad trade
predict PASS → KEEP → test → see the real failure → repair predict failure → REVISE → no feedback, one call spent The predictive signal could be useful while the action attached to it was not.
Scope
This split is still correlational. Harder patches may be more likely to trigger REVISE in the first place. A forced-KEEP ablation is needed to isolate the effect.

What the predictive agent learned

The predictive agent learned a real outcome distinction

The Arm B SFT checkpoint effectively predicted PASS for everything. After RLVR, the policy learned a nontrivial RUNTIME_ERROR distinction.

Step 100, seed 42. Runtime errors were only about 16% of evaluation outcomes, and the SFT checkpoint never predicted the class correctly.

62.5%
RUNTIME_ERROR precision, seed 42
64.1%
RUNTIME_ERROR precision, seed 43
✓ A real but incomplete distinction
RUNTIME_ERROR recall reached about 63% in seed 42, with precision of 62.5% and 64.1% across the two seeds. Prediction frequency roughly matched real frequency, rather than simply over-predicting the class. ASSERTION_FAILURE, which made up roughly 57% of evaluation outcomes, remained at 0% recall. The experiment does not isolate the auxiliary CE term itself; an alpha = 0 ablation is required for that attribution.

Limitations

What the experiment leaves open

The recovery examples used during SFT were synthetic mutations of correct MBPP solutions rather than failures sampled from the policy itself. That likely made the SFT failure distribution different from the failures the model later produced during RL.

Outcome classes were inferred heuristically from execution errors, so the fine-grained failure labels contain some noise.

MBPP was a weak environment for prediction-before-action. Even a perfect outcome predictor has little advantage when execution is cheap: running the test costs one tool call and directly reveals the outcome the prediction is trying to anticipate.

What this shows
This is the winning strategy, and it is the baseline's strategy. Two logical failures labelled PASS, three KEEPs, three tests, reward 1.0, with recovery entirely on visible test feedback, exactly like Arm A. The 0% ASSERTION_FAILURE recall and the 63.3% never-revised pass rate in one trace.
Verifier gap
The final solution used *, even though the task banned it, but still received reward 1.0 because the tests checked only the output. Arm A followed the instruction correctly. One case, but it shows the verifier can reward solutions that pass tests while violating the task.

How it works

How the training signal works

Suppose the agent writes a patch, predicts <PREDICTION>PASS</PREDICTION>, commits to <DECISION>KEEP</DECISION>, and the patch actually produces RUNTIME_ERROR.

The rollout that happened

prefix → PASS → KEEP → execute → RUNTIME_ERROR the sampled PASS label loses its RL credit, so reward never reinforces it

The sample PREDICT adds

same prefix → RUNTIME_ERROR CE-only: rl_weights = 0, ce_weights = alpha on the verified-label tokens

The sampled PASS label is excluded from RL credit. After the rollout, the verified RUNTIME_ERROR target supervises the model at that earlier point in the trajectory. ECHO applies auxiliary prediction loss to environment observations already present in the rollout; PREDICT constructs a verifier-derived target at an earlier pre-execution state.

Why the target does not have to be in the rollout
This supervision also works when the verified outcome never appeared in the visible rollout for example when a rejected patch is evaluated through shadow execution. The label is manufactured by the verifier after the fact and rendered onto the pre-execution context as its own training sample.

What would settle it

Three ablations this design still owes

Arm A vs. Arm B compares two complete systems, so it cannot say which piece mattered. Each of these holds Arm B fixed and changes one factor.

01
alpha = 0

Arm B with the same prediction and KEEP/REVISE protocol, same trace format, same action budget, but no verified-label CE. If the learned outcome distinction survives, it came from the protocol or from GRPO on the surrounding tokens, not from the auxiliary loss.

02
Forced KEEP

Keep the prediction and the CE, disable REVISE, make every decision a KEEP. If pass@1 recovers, the decision gate is the failure mode. Without it the REVISE split stays correlational: revised rollouts are also the ones the model already judged risky.

03
Budget-neutral REVISE

Make REVISE free, or raise the tool budget past exhaustion. This tests the strongest mechanism claim directly. If the deficit survives a budget that cannot be exhausted, the cost is discarding a patch without observing why, not the spent action.
