PREDICT

Reactive vs. Predictive Post-Training for Coding Agents

X · jayzenith.me · GitHub

PREDICT began with a broader question: can an agent learn to predict the outcome of its own actions before observing the result?

I used coding as the testbed because patches have clear, verifiable outcomes, and because I wanted to understand the post-training stack end to end by actually training an agent.

I compared two Qwen3-4B agents in the same coding environment. Arm A reacts to test feedback. Arm B predicts the outcome of each patch before execution, decides whether to keep or revise it, and is trained using the verified outcome afterward.

Both agents improved over their SFT checkpoints, but Arm B did not outperform the reactive baseline. The interesting part was why.

The predictive agent learned a real, although incomplete, ability to anticipate some failures. But REVISE was badly matched to this environment. It removed useful test feedback while consuming part of a limited tool-call budget. On MBPP, simply running the test was usually more useful than predicting its result.

1. Agent design

The difference between the two agents happens immediately after a patch is written.

Arm A follows the normal coding-agent loop:

patch → test → observe result → repair

Arm B inserts a prediction and decision before the test:

patch → predict outcome → KEEP or REVISE

Arm B predicts one of six execution outcomes:

PASS
ASSERTION_FAILURE
RUNTIME_ERROR
SYNTAX_ERROR
TIMEOUT
OTHER

The decision then determines what the agent gets to observe.

KEEP

patch → prediction → KEEP → visible test → feedback

The patch runs, and the model sees the result.

REVISE

patch → prediction → REVISE → another patch

The rejected patch is still executed in the background. This hidden execution lets the training system recover the true outcome of the patch, but that result is not shown to the model during the rollout.

So there are two different things happening: KEEP gives information to the agent. Shadow execution after REVISE gives information to the training system. Everything else about the environment is shared between the two arms.

2. How PREDICT is trained

The key idea is to use an outcome that becomes known later to supervise a prediction made earlier.

Suppose the model writes a patch and predicts:

<PREDICTION>PASS</PREDICTION>

It then chooses:

<DECISION>KEEP</DECISION>

The patch runs and actually produces:

RUNTIME_ERROR

The rollout therefore contains:

context → PASS → KEEP → execute → RUNTIME_ERROR

The sampled PASS prediction is excluded from the RL loss. The eventual task reward does not reinforce that prediction token simply because it appeared in the rollout. After execution, however, the verifier knows that the correct prediction was RUNTIME_ERROR.

PREDICT then constructs a separate supervised example from the same context that existed immediately before the prediction:

same context → RUNTIME_ERROR

That additional example is CE-only:

rl_weights = 0
ce_weights = alpha on the verified outcome-label tokens.

The model therefore receives direct supervision for what it should have predicted at that earlier point.

Rollout

context → sampled PASS gets RL credit → KEEP → execution → verified RUNTIME_ERROR

Separate supervised example

same pre-prediction context → RUNTIME_ERROR CE loss applies only to the verified label.

This also works when the model chooses REVISE. The rejected patch is executed in the background. The result stays hidden from the agent, but the verifier can still use it to construct the supervised prediction target.

So the central mechanism is:

the rollout contains the model's own prediction, while training later creates a separate example containing the verified prediction that should have been made from the same earlier context.

This is related to ECHO-style auxiliary prediction training, but the target here is verifier-derived and attached to an earlier pre-execution state rather than simply predicting an observation already present in the visible rollout.

3. Experiment

Both arms used Qwen3-4B-Base and were first supervised-fine-tuned before RL.

The dataset split was:

212 SFT tasks
142 direct solutions and 70 recovery traces
212 RL tasks
disjoint from SFT
40 validation tasks
used for checkpoint selection
500 final evaluation tasks

Both arms were trained with two RL seeds. The final test set was evaluated after the experimental design was fixed. The experiment was intentionally narrow: one model family, one coding environment, two RL seeds, and a limited post-training budget.

MBPP consists of short Python programming problems evaluated using test assertions.

That leaves a more useful question:

Why didn't prediction help?

5. REVISE was the main failure mode

The clearest difference appears when Arm B trajectories are split by whether the model ever chose REVISE.

Among trajectories that never used REVISE, final pass rates were:

63.3% in seed 42
60.4% in seed 43

Among trajectories that used REVISE at least once, pass rates were:

1.1% in seed 42
4.9% in seed 43
seed 42 seed 43

The gate was not completely random. Arm B chose REVISE more often when a patch would actually fail than when it would pass:

Seed 42: 22.2% on failing patches vs. 8.5% on passing patches
Seed 43: 14.3% on failing patches vs. 4.2% on passing patches

So the decision contained some real signal. The problem was what happened after the signal was used.

If the model predicts PASS and chooses KEEP:

patch → predict PASS → KEEP → test → observe failure → repair

Even though the prediction was wrong, the model gets useful information from the test.

If the model predicts failure and chooses REVISE:

patch → predict failure → REVISE → no test feedback → another patch

The model may have correctly recognized that something was wrong, but it does not learn what went wrong. REVISE also consumes a tool call. The agents had an 8-call budget.

Among trajectories that used REVISE:

99% exhausted the budget in seed 42
95% exhausted the budget in seed 43

Among trajectories that never revised:

35% exhausted the budget in seed 42
37% exhausted the budget in seed 43

So the protocol created a bad trade. A wrong PASS prediction followed by KEEP still gave the agent the information needed to recover. A correct failure prediction followed by REVISE removed that information while leaving less budget for recovery.

That does not prove that REVISE itself caused the entire performance gap. The split is correlational. Harder patches may naturally be more likely to trigger REVISE. A forced-KEEP ablation is needed to isolate that effect.

6. Did the model actually learn to predict outcomes?

Yes, but only partially

One possible explanation for the result would be that Arm B simply failed to learn prediction at all. That is not what happened. At the SFT checkpoint, Arm B effectively predicted PASS for everything. After RL, it developed a nontrivial ability to recognize RUNTIME_ERROR.

In seed 42:

PASS recall: 92%
RUNTIME_ERROR recall: about 63%
ASSERTION_FAILURE recall: 0%

Runtime errors represented only about 16% of verified evaluation outcomes, while assertion failures represented roughly 57%.

RUNTIME_ERROR precision was:

62.5% in seed 42
64.1% in seed 43

So the model had learned a real distinction about which patches were likely to crash. But it did not learn the much more common distinction between code that executes and code that executes successfully but produces the wrong answer. That is an important limitation of the learned predictor.

There is also a causal limitation. Arm B was trained using both GRPO and the auxiliary verified-outcome CE objective. Because I did not run an alpha = 0 version of Arm B, this experiment cannot establish that the auxiliary CE term itself caused the learned runtime-error distinction. What the experiment shows is that the distinction emerged during the combined training procedure.

7. Why MBPP was a weak environment for prediction-before-action

The original idea only becomes valuable when knowing a consequence before acting is meaningfully better than simply observing the consequence afterward. MBPP does not strongly satisfy that condition. Running a test costs one tool call. That test directly tells the model whether the patch worked.

The reactive agent can therefore do:

patch → test

and immediately receive the information Arm B is being trained to predict. Even a perfect predictor has limited room to add value when verification is already this cheap.

At the same time, the predictive protocol introduced a real cost. REVISE could prevent the model from seeing the test feedback it would otherwise have received. So this experiment does not show that prediction-before-action is generally useless.

It shows that prediction had little opportunity to create value in an environment where checking the consequence was already cheap, while acting on a negative prediction carried an additional cost. Prediction should matter more in environments where consequences are expensive, delayed, risky, or difficult to reverse.

8. Other limitations

The SFT recovery examples were synthetic mutations of correct MBPP solutions rather than failures sampled from the policy itself. That means the failures shown during SFT may have differed substantially from the failures the model later generated during RL. This distribution mismatch may help explain why the model learned some outcome distinctions but completely failed to learn ASSERTION_FAILURE.

The fine-grained outcome classes also contain some noise because they are inferred heuristically from execution errors.

Finally, this was a small experiment: one model family, one benchmark, two RL seeds, and a limited post-training budget. The results are evidence about this particular mechanism and environment, not a general conclusion about predictive agents.

9. What I would run next

Three experiments would separate the main pieces of Arm B.

alpha = 0

Keep Arm B's prediction and KEEP/REVISE protocol exactly the same, but remove the verifier-derived auxiliary CE loss. If the learned outcome distinction remains, then it came from the protocol or from GRPO acting on the surrounding behavior rather than from the auxiliary objective itself.

Forced KEEP

Keep prediction and the auxiliary CE objective, but disable REVISE. Every patch is predicted and then executed normally. If pass@1 recovers, that would provide much stronger evidence that the REVISE mechanism was responsible for the performance deficit.

Budget-neutral REVISE

Keep REVISE, but either make it free or increase the tool budget enough that exhaustion is no longer relevant. If revised trajectories still fail, then the important cost is likely the loss of execution feedback rather than the spent tool call.

10. Implementation

PREDICT is built on Prime Intellect's PRIME-RL and Verifiers stack. GlyphTaskset loads the coding tasks, prepares the runtime environment, and computes reward and rollout metrics. GlyphHarness launches each coding-agent rollout in a confined subprocess environment.

The rollout program implements the actual agent loop:

model → tool call → patch → prediction/decision → execution → next model turn

It also records the verifier-derived prediction targets used after the rollout. PredictAlgorithm determines how the resulting tokens and samples participate in training. Normal rollout tokens participate in GRPO, sampled prediction-label tokens are masked out of RL credit, and the verified prediction targets become separate CE-only training samples.

PRIME-RL then performs the actual batching, loss computation, backpropagation, optimizer updates, and synchronization of the updated model weights. The repository contains the environment, SFT and RL configurations, auxiliary training logic, evaluation code, published results, version pins, and reproduction documentation.
